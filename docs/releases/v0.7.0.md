## Whatever v0.7.0 - Custom components, scene snapshots and modding docs

Mods can now define their own components as ordinary TypeScript classes, edit their fields in the native editor, and read the scene without sending a request for every lookup. This release also adds native performance measurements, the Markbench benchmark mod, and a dedicated modding documentation website with the actual host IPC contract.

The rule stays the same: the engine supplies the services, and every game is an ordinary mod collection.

### Your own components, in code and in the editor

Export a named class extending `Component` from your mod's local source. Public writable fields become persisted component data and Inspector fields; private state stays inside the mod process.

```ts
import { Component, Type, field } from "@whatever-engine/api";

export class Health extends Component {
  static readonly type = "my_game:health";

  value = field(Type.I32.with({ min: 0, max: 100 }), 100, {
    label: "Health",
    tooltip: "Current hit points.",
  });

  override start() {
    this.entity.addTag("damageable");
  }
}
```

Components have `start`, `tick`, `onEnable`, `onDisable`, and `destroy` hooks. Async startup and ticking do not overlap, and disabled entities or ancestors pause their components. Removing and reattaching a component creates a fresh instance, even when both happen in one batch.

The host and editor inspect source metadata without evaluating mod code. Custom components appear in Add Component with defaults, labels, tooltips, numeric constraints, enum choices, and entity/asset selectors. Refresh component types after source changes and restart Play to load the new code; this is not script hot reload.

### Shared schemas and entity tags

`Type`, `Struct`, `Infer`, and `field` provide a shared schema system for components and networking. Component schemas support nested objects, arrays, tuples, enums, nullable values, entity references, and asset paths. Native validation checks both schemas and writes; the network codec continues accepting its supported subset.

Entities can carry up to 32 unique tags. Use `addTag`, `removeTag`, `hasTag`, `getTags`, `Scene.findByTag`, and `Scene.findByTags` to organize and find them. Tags persist in scene files, survive cloning, and can be edited in the Inspector, including during Play.

### Scene reads without a round trip

Every scripted mod now receives a revisioned scene view. Synchronous entity, component, hierarchy, camera, and tag reads use that view plus the mod's own queued commands. You can record a create, configure it, and inspect your local changes before the native result arrives.

The engine publishes creates, removals, changed component values, and entity metadata after command execution and physics. Mutation journals avoid rebuilding unchanged component values, and each encoded delta is shared across native pipe writers. Each host still owns its decoded store; this is not shared-memory ECS access.

`Scene.snapshot()` retains an immutable committed revision. `getComponent` also returns immutable field data. Use a detached edit draft to change a component:

```ts
entity.editComponent("core:transform", (transform) => {
  transform.setScaleUniform(2);
});
```

Explicit `requestComponent`, `requestQuery`, `requestParent`, `requestChildren`, and `requestMainCamera` methods remain available when a result must reflect its exact position in the native command buffer. Call `.get()` to await an already recorded request.

### Profiling and Markbench

`Profiler` exposes a monotonic clock, host memory usage, native tick CPU phases, and client frame measurements. Samples distinguish command execution, physics, snapshot work, presentation, surface acquisition, encoding, submission, and present calls. Server samples have no frame data; GPU execution time is currently unmeasured.

The new `markbench` mod supplies deterministic workloads, warmup and sampling, scoring, and reports. It replaces the old small debug benchmark and can be excluded from game exports through ordinary project build settings. See the [Markbench guide](https://github.com/MesterMan03/Whatever/blob/v0.7.0/games/test/mods/markbench/README.md) for workload and score definitions.

### A proper modding documentation site

The new Astro Starlight site brings the scripting reference, editor workflow, and modding guides together with search, light/dark themes, mobile navigation, and copyable examples.

- A first-mod tutorial, custom component examples, and guides to scenes, client/server code, debugging, and packaging.
- Focused API reference pages generated from the existing Markdown documentation.
- A standalone IPC specification covering startup, one-batch-per-tick execution, requests and responses, scene revisions, references, failures, limits, and shutdown.
- A message-field catalogue generated from the native Rust definitions, plus detailed nested physics/network request and event shapes for compatible implementations.
- GitHub Pages CI that builds and checks the site, type-checks its tutorial examples, and deploys from `main` once Pages is configured.

The protocol docs distinguish an alternative API implementation from runtime permissions: ordinary mods still cannot replace the bundled host, acquire raw pipe handles, or import unrestricted npm and Node/Bun modules.

### Other improvements

- Development host discovery can skip stale bundled candidates and reports the exact compatibility mismatch. Release builds continue requiring their own compatible bundled host.
- Native host protocol **10** carries revisioned scene deltas and performance samples. Compatibility is checked before mod evaluation.
- Live editor snapshots are throttled independently of simulation ticks.
- Editor inspectors use the same registered component definitions and validation as the player.
- Game/mod versions and protocol/schema versions remain independent of the shared Whatever release version.

### Updating from 0.6.0

All engine crates, the editor, launcher, `wmod`, and `@whatever-engine/api` are **0.7.0**. Update the API declarations and rebuild the bundled host together with the engine.

This release includes scripting API changes:

- Replace raw `setComponent("type", data)` calls with registered native or custom class instances, such as `entity.setComponent(new BuiltInComponents.Transform())`. The raw overload and `Scene.setComponent` are removed.
- Synchronous `getComponent`, entity-list, query, and hierarchy methods return local scene data. Component snapshots are read-only and do not expose mutable class helpers. Use `editComponent` or set a new component instance to write.
- For an ordered native query, use its explicit `request*` method and await `.get()`.
- Entity creation and spawn/clone helpers return immediately usable `PendingEntity` references; `.get()` waits for confirmation when needed.
- Keep component modules free of top-level scene mutations. Initialize game state in `start()` or an `init` handler.
- Source/schema changes require restarting Play. Game, mod, and scene-file versions do not need to match the engine release number.

### Portable downloads

The release workflow promotes the exact archives from successful **Windows x86_64**, **Linux x86_64**, and **macOS arm64** editor CI builds, together with `SHA256SUMS`. Each package includes the editor, player, launcher, bundled mod host, core template, CLI, and API SDK. Extract the whole archive and keep its files together; installed distributions do not require Rust or a system Bun installation.

Linux targets the Ubuntu 24.04 build environment and still uses system graphics/display drivers. The macOS app is ad hoc signed and is not notarized.
