## Whatever v0.6.0 - Native editor, physics and multiplayer

This is a pretty huge update. Whatever now has an actual native editor, scene files, native physics and networking, plus a proper way to build and ship games. The engine is still just the backend: a game is a collection of mods, and a finished game can be opened in the same editor as a project you're working on.

### The Whatever Editor

The editor is a separate desktop app, sharing engine and project code with the player and the `wmod` CLI.

- A welcome screen, recent projects, native menus and file/folder pickers.
- A scene hierarchy with drag and drop parenting and ordering, entity presets, enable/disable toggles, copy/paste, duplication, renaming and undo/redo.
- A scene viewport with entity picking and move, rotate and scale tools, axis highlighting, configurable snapping and component handles for things like colliders and joints.
- Proper inspectors for built-in rendering, camera, lighting and physics components, including entity reference pickers.
- Folder browsers for assets, scenes and scripts, mod metadata editing, and a configurable external script editor.
- Live inspection while playing: the hierarchy shows the running game's entities, and the inspector can change them. Separate Scene and Play tabs let you use the editor camera while the game keeps running. These changes are discarded when Play stops.

On Windows, Play embeds the player in the editor. Shift-click Play opens a separate window. Linux and macOS use a separate player window, with a Play camera preview in the editor.

### Scene files

Scenes are versioned `.wscene` files owned by mods. They store entity hierarchies, components, enabled states and references between entities. Loading a scene creates fresh entity IDs, remaps its references and validates the whole scene before applying it.

Scripts can load scenes through `Scene.loadScene("my_mod://main")`. The core mod can also specify an `initial_scene` in its `mod.toml`, which is loaded before scripts initialize. The built-in console command `scene load <mod_id://scene>` uses the same loader.

Entities can now be cloned, including child hierarchies and internal references. The physics demo uses an authored scene with a disabled cube template and a spawn point, rather than constructing its entire scene in code.

### Building a game

The editor's Build button supplies the player, bundled mod runtime and native libraries automatically. No manually assembled runtime kit is required. Build settings cover game branding, icons and mods to exclude, so development tools can stay in your project without being shipped.

A Windows build contains your branded `<Game Name>.exe`, the engine files, a separate `runtime.exe` and the selected mods. The small launcher starts the ordinary engine; the game's behavior still comes entirely from mods. Project identity and the deployed core metadata stay in sync.

`wmod` is now the CLI companion for creating projects and mods, checking collections and packaging games. It uses the same project and deployment code as the editor.

### Native physics

Rapier physics is available through components and the scripting API: physics worlds, rigid bodies, colliders, joints, queries, forces and collision events.

Joints belong to the first body and reference a connected body. The editor provides body pickers and viewport handles for editing joint positions and collider shapes. The physics demo has also been reorganized around scene entities, including a grouped gate.

### Networking and headless servers

The engine now provides native QUIC transport with TLS, typed packet schemas and codecs, streams and datagrams, certificate trust handling and typed per-client data. Game protocols remain in mods.

Mods can define separate client and server entry points. `--mode server` starts a headless runtime with the same simulation and console command system. The network example includes a small multiplayer messenger for exercising the transport and trust flow.

### Simulation and scripting

Simulation now runs on its own worker, independently of window rendering. Mods submit ordered command batches each tick; commands execute in dependency/load order, then physics runs, then results and world snapshots are published.

The scripting API uses pending results for commands and queries. Chains can be recorded together and resolved through `.get()`. This is a substantial API change, so existing mods should follow the updated scripting reference.

Each scripted mod runs in a separate bundled native host built from the pinned Bun fork. The runtime is shipped separately from the player executable. Native import and global policies allow the engine API and local JS/TS/JSON sources, while denying non-allowlisted built-ins, npm packages and host capabilities.

### Fixes and improvements

- Rendering interpolates published simulation poses, making cameras and moving objects smoother when rendering faster than the tick rate.
- Frame caps use consistent deadlines and the FPS counter measures elapsed time.
- Mouse input is cleared when capture is released; uncaptured mouse movement is not sent as tick deltas. Embedded Play also handles capture, console input and focus changes.
- Branded launchers bring the game window forward on Windows.
- Restarting a QUIC listener waits for the previous UDP socket to close before rebinding its port.
- The mod host uses private descriptor I/O for complete UTF-8 batches over the player's OS pipes.
- Fixed sustained Windows ticking stalls in the pinned runtime's parallel garbage collector and macOS host startup under Seatbelt.
- Console command collisions qualify every participant as `<namespace>:<command>`. Engine commands use `core`; a core-mod collision is an error instead of silently replacing a command.
- Fixed asset browser items stepping diagonally, missing menu glyphs, modal dialogs allowing clicks through to the editor, undo losing selection, and Windows editor startup stack exhaustion.
- Fixed CI failures involving mixed Windows LLVM tools, trusted module cache exposure, Linux path allocation and Windows checkout line endings.

### Portable downloads

This release includes the editor for **Windows x86_64**, **Linux x86_64** and **macOS arm64**, plus SHA-256 checksums. Extract the archive and keep its contents together. The packages include the player, launcher, mod host, core template and API SDK; Rust and a system Bun installation are not required.

Each platform is built and tested in CI, including a relocation test that creates and packages a game using the installed files and starts its branded launcher in headless mode.

Linux targets the Ubuntu 24.04 build environment and still uses system graphics/display drivers. The macOS app is ad hoc signed and is not notarized.

### Updating from previous versions

- All engine crates, the editor, launcher, `wmod` and `@whatever-engine/api` are **0.6.0**. Game and mod versions remain independent.
- The source checkout's test project now lives in `games/test`, including its `whatever.wproject` and mods.
- Update mods for the pending command API, scene format and client/server entry selection where applicable.
- Mods should use the engine API for host services; unrestricted Node/Bun built-ins and npm imports are not available in the bundled runtime.
